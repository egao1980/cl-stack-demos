== Demo 2: the TOTAL deadline and the read timeout, HTTP and HTTPS (#24)
========================================================================
Each origin stays silent after the request head, then answers.
  http, silent 5 s, :timeout 2.0                       => HTTP-TIMEOUT-ERROR: dexador: total timeout after 2.0 s after 2.01 s
  https, silent 5 s, :timeout 2.0                      => HTTP-TIMEOUT-ERROR: dexador: total timeout after 2.0 s after 2.01 s
  https, silent 6 s, (:connect 5 :read 1)              => HTTP-TIMEOUT-ERROR: dexador: read timeout after 1.0 s after 1.02 s
  http -> 301 -> https, silent 6 s, (:connect 5 :read 1) => HTTP-TIMEOUT-ERROR: dexador: read timeout after 1.0 s after 1.02 s
  https, silent 6 s, (:read 1.5)                       => HTTP-TIMEOUT-ERROR: dexador: read timeout after 1.5 s after 1.52 s
  (0.1.5: both https rows with :read returned the response after 6 s; the TLS reads
   went through cl+ssl's socket BIO, which never sees the fd-stream timeout)

The read timeout bounds silence, not the whole body:
  https, 8 octets 0.5 s apart, (:read 1) => HTTP-RESPONSE 200, body "........", after 4.06 s

A streamed HTTPS body (:want-stream t) keeps the read timeout after send returns:
  send => HTTP-RESPONSE 200 after 0.02 s (headers only)
  first body read, the origin silent for 6 s => HTTP-TIMEOUT-ERROR: dexador: read timeout after 2.0 s on the response body after 2.01 s

== Demo 4: request bodies reach the origin as encoded (#32)
========================================================================
Each POST goes to a loopback origin that records the head and body it reads.
0.2.0 handed dexador http-protocol's encoded octets, and dexador encodes a
body again when its Content-Type is application/x-www-form-urlencoded or multipart/*.

  :form-data (("key1" . "value1"))  (0.2.0: QURI.ENCODE::PARAMS-ALIST is #(107 101 ...), not a LIST)
    => HTTP-RESPONSE 200
    origin read "Content-Type: application/x-www-form-urlencoded"
                Content-Length: 11, body "key1=value1"

  :data (("q" . "hi there"))  (an alist :data is urlencoded too; 0.2.0: the same error)
    => HTTP-RESPONSE 200
    origin read "Content-Type: application/x-www-form-urlencoded"
                Content-Length: 10, body "q=hi+there"

  :form-data "city=Zürich"  (a string goes as UTF-8)
    => HTTP-RESPONSE 200
    origin read "Content-Type: application/x-www-form-urlencoded"
                Content-Length: 12, body "city=Zürich"

  :form-data (("k" . "v")) :files (("f" . "file body"))  (0.2.0: refused as a stream body)
    => HTTP-RESPONSE 200
    origin read "Content-Type:  multipart/form-data; boundary=----cl-stack-69064fe49d38006318d9dc70a0a533cd"
                Content-Length: 308, body "------cl-stack-69064fe49d38006318d9dc70a0a533cd\r\nContent-Disposition: form-data; name="k"\r\n\r\nv\r\n---..."

  pre-encoded multipart :content  (0.2.0: TYPE-ERROR in dexador's MULTIPART-CONTENT-LENGTH)
    => HTTP-RESPONSE 200
    origin read "Content-Type:  multipart/form-data; boundary=XyZ"
                Content-Length: 63, body "--XyZ\r\nContent-Disposition: form-data; name="k"\r\n\r\nv\r\n--XyZ--\r\n"

  :form-data (("key1" . "value1")) :content-encoding :gzip  (0.2.0: refused as a stream body)
    => HTTP-RESPONSE 200
    origin read "Content-Type:  application/x-www-form-urlencoded"
                Content-Encoding: gzip, Content-Length: 31, 31 octets that decode to "key1=value1"
    (the leading space in the last three Content-Type values is optional whitespace,
     RFC 9112 §5, which the origin strips; it keeps dexador from encoding the body again)

  JSON :content with Content-Type application/json  (worked in 0.2.0 too)
    => HTTP-RESPONSE 200
    origin read "Content-Type: application/json"
                Content-Length: 7, body "{"a":1}"

The #32 report through http-protocol's facade, http:post :form-data:
  (http:post url :form-data '(("key1" . "value1"))) => HTTP-RESPONSE 200; the origin got "key1=value1"

== Demo 5: redirects and response-history (#33)
========================================================================
0.2.0 let dexador follow redirects and kept only the last response, so
response-history was always empty. 0.2.1 follows them in the backend.

  GET /r/2 (302 → /r/1, 301 → /r/0) => HTTP-RESPONSE 200, url http://127.0.0.1:P/r/0
    response-history: 302 http://127.0.0.1:P/r/2, 301 http://127.0.0.1:P/r/1

  POST /form :form-data, 303 → /done => HTTP-RESPONSE 200
    response-history: 303 http://127.0.0.1:P/form
    origin: POST /form HTTP/1.1, Content-Type application/x-www-form-urlencoded, 11 body octets
    origin: GET /done HTTP/1.1, Content-Type none, 0 body octets
    (dexador's own redirect sent the GET with the POST body, its Content-Type
     and Content-Length again, and Host without the port)

  POST /keep, 307 → /kept => HTTP-RESPONSE 200
    origin: POST /keep HTTP/1.1, body "abc"
    origin: POST /kept HTTP/1.1, body "abc"

  GET /loop (302 → /loop), :max-redirects 3 => HTTP-REDIRECT-ERROR: http-backend-dexador: exceeded max-redirects (3) at http://127.0.0.1:P/loop
    the origin saw 4 requests (0.2.0 returned the 4th 302 as the response)

  GET A/go with basic auth, 302 → B/there => HTTP-RESPONSE 200
    response-history: 302 http://127.0.0.1:P/go
    A got Authorization: yes
    B got Authorization: no, Host: 127.0.0.1:P (B listens on port P)
    (0.2.0 sent Host: 127.0.0.1 to B, without the port)
