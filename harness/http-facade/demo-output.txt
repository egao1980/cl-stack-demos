== Demo 4, continued: a redirect through the proxy (http-backend-async#82)
========================================================================
Each run follows one 301 on http-backend-async. The session's :proxy (cl-stack-http#34) names
loopback proxies (redirect-proxy.lisp) that play origin.test themselves; no proxy variable is set.
One https:// or http:// proxy URL serves both schemes, or a per-scheme table names a plain one
for http:// and a TLS one for https://.
The proxy URLs carry user:secret, the request :auth alice:made-up (both made up). The proxy
logs the head it reads, and the head the origin reads inside a CONNECT tunnel. Each hop is
built for its own URL: http:// in absolute-form with Proxy-Authorization, https:// through
CONNECT with none inside the tunnel, the proxy picked again, Authorization dropped on another
origin (here, another scheme).
Before: 0.2.29 sent the https:// hop into the tunnel as GET https://origin.test/b with
Proxy-Authorization and Authorization, the http:// hop to the proxy as GET /b without
Proxy-Authorization (a proxy cannot route that: 400), and kept the first hop's proxy.

== Demo 4, continued: which proxy a session uses (cl-stack-http#34, #35)
========================================================================
http_proxy names a loopback proxy, and two more stand by for the session's :proxy and the
request's. Each request is GET http://origin.test/p; origin.test does not resolve, so a
request that goes direct fails. As in requests: a request :proxy wins over the session's,
the session's over the environment, which applies under :trust-env (the default);
:trust-env nil does not read it.
Before: cl-stack-http 0.2.0 gave each request the system proxy config, which wins over the
session's, so a session :proxy went through http_proxy (or direct when none was set), and
:trust-env nil still went through http_proxy (http-protocol's default config reads it).
  dexador  session :proxy                  => 200 "the origin, http://origin.test/p"
                                            read by: the session proxy
  dexador  session and request :proxy      => 200 "the origin, http://origin.test/p"
                                            read by: the request proxy
  dexador  no :proxy                       => 200 "the origin, http://origin.test/p"
                                            read by: the env proxy
  dexador  no :proxy, :trust-env nil       => NS-HOST-NOT-FOUND-ERROR: Condition USOCKET:NS-HOST-NOT-FOUND-ERROR was signalled.
                                            read by: nobody (direct)
  dexador  session :proxy, :trust-env nil  => 200 "the origin, http://origin.test/p"
                                            read by: the session proxy
  async    session :proxy                  => 200 "the origin, http://origin.test/p"
                                            read by: the session proxy
  async    session and request :proxy      => 200 "the origin, http://origin.test/p"

  async    no :proxy                       => 200 "the origin, http://origin.test/p"

                                            read by: nobody (direct)
  async    session :proxy, :trust-env nil  => 200 "the origin, http://origin.test/p"

== Demo 5: a redirect keeps HEAD and its connection (http-backend-async#84, #85)
========================================================================
The origin answers /redirect/S with S and Location: /target over keep-alive connections;
it logs each request's method, connection and body. Each run is one request in a new session;
sessions share the backend's pool, so a run can start on the connection the last one left.
RFC 9110 §15.4: 303 turns anything but HEAD into GET, 301 and 302 turn only POST into GET,
and a method that stays sends its body again.
Before: http-backend-async 0.2.30 sent GET /target after a HEAD's 301, 302 or 303 and got a
body; both backends turned a 301/302 PUT or DELETE into a GET without its body; and async
closed the redirect's kept-alive connection, so /target came on a second one (#85).
