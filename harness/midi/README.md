# MIDI demo: building, reading and repairing Standard MIDI Files

`harness-demos-midi` is a tour of **midi-protocol 0.1.0** from GHCR. The library models MIDI 1.0 messages and reads and writes Standard MIDI Files (SMF) of type 0, 1 and 2. It works with files only: no real-time ports and no MIDI 2.0. Events are immutable structs, a track is a list of events, and an SMF is a header (format and division) plus a list of tracks.

The demo uses one short piece, "Twinkle, Twinkle, Little Star", whose tune and words are in the public domain. It builds the piece in code, writes it, reads it back, times it, breaks the bytes in several ways and repairs them, then lets mido read the result. Every result with a known answer is checked (103 checks, 95 when uv is missing), and the summary line reports the mismatches. Everything is in [`src/demo.lisp`](src/demo.lisp). [`demo-output.txt`](demo-output.txt) is the output of the last run, on macOS arm64 with SBCL 2.6.9, with home and temp paths replaced by `~` and `<tmp>`. [`twinkle.mid`](twinkle.mid) is the file the run writes (527 bytes): any MIDI player can play it.

## Run

```bash
cd harness/midi
cl-repo run -- sbcl --non-interactive --no-userinit --eval '(require "asdf")' \
  --eval '(asdf:load-system "harness-demos-midi")' \
  --eval '(harness-demos-midi:run-demos)' > demo-output.txt 2>&1
```

It needs SBCL and `cl-repo`. Section 8 also needs [uv](https://docs.astral.sh/uv/) on `PATH`, and fetches mido 1.3.3 from PyPI on its first run. Without uv, section 8 prints a note and is skipped, as midi-protocol's own tests skip their mido cross-read. Apart from that one download there is no network step. A run takes about five seconds with `cl-repo run`, most of it start-up and the mido subprocess. `run-demos` returns `NIL` when a check fails or a section stops on an error, and CI then exits 1.

## What each section shows

1. **Build a type-1 SMF and write it.** The piece is in C major and 4/4, at 480 ticks per quarter note, and has two phrases of two bars. There are three tracks. The tempo track holds the title (`track-name-event`), time signature, key signature, tempo (100 bpm, then 80 bpm from bar 3) and two markers. The melody track is a flute on channel 0: track name, program change, volume and pan controllers, then for each note a `lyric-event` with the syllable, a `note-on-event` and a `note-off-event`. The bass track has root and fifth together on channel 1. Each track is built from (tick . event) pairs with `track-from-absolute`. `write-smf` with destination `NIL` returns 527 octets. The 14-byte header is dumped field by field. Each event of the tempo track is then shown with its file offset, delta and bytes, so you can see the delta time as a variable-length quantity (3840 is `9E 00`), the 24-bit tempo (`09 27 C0`), and the time signature's denominator stored as a power of two. The event bytes are checked against hand-written hex.
2. **Read it back.** `read-smf` returns an SMF that is `equalp` to the one written, and writing that again gives the same 527 bytes. Every event of the three tracks is listed with its delta, its absolute tick and a description. Events print readably as `#S(MIDI-PROTOCOL:NOTE-ON-EVENT ...)` and read back `equalp`. `copy-event` makes a changed copy (`:key`, `:channel`) and leaves the original as it was.
3. **Running status.** The file is written with and without `:running-status`: 527 against 545 bytes. A table gives the saving per track, which equals the number of channel events that repeat the status of the event before them. In the melody that is one byte, because every note-on follows a lyric (a meta event resets running status). In the bass it is 17 bytes, because the second note-on and the second note-off of each pair go without a status byte. The first bass events are shown encoded both ways (`00 2B 46` against `00 91 2B 46`). Both files read back to the same events, and the longer one written again with the default gives the shorter one byte for byte.
4. **Absolute time.** `track-to-absolute` and `track-from-absolute` round-trip the melody. Events at the same tick keep their input order, so pairs given in reverse put a note-on before the note-off of the same key at tick 480, which would cut the note short. `merge-tracks` makes the type-0 view: 90 events, 17 of them at tick 0 in track order, 493 bytes, every event at its original tick. `tempo-map` gives `((0 . 600000) (3840 . 750000))` for the piece and `((0 . 500000))` (`+default-tempo+`) for a track with no tempo event. `ticks-to-seconds` gives exact rationals: a table shows when each syllable is sung (`I` at 111/20 s, the end at 54/5 s), checked against a hand calculation, plus results with no tempo map and with SMPTE divisions (25 fps, and 29.97 drop frame). A type-2 SMF holds two independent patterns, the tune at 100 bpm and a copy a fourth up at 150 bpm. Each pattern gets its own tempo map, and the section shows what `tempo-map` returns for the whole type-2 SMF, where the tracks are merged.
5. **Bad bytes: `midi-parse-error` and its restarts.** A file cut 20 bytes short fails at offset 507 in track 2, with `skip-chunk` and `use-partial-smf` on offer. `use-partial-smf` keeps the two whole tracks and the start of the bass, and `skip-chunk` drops the bass. Every one of the 527 proper prefixes fails at its own length, and `use-partial-smf` on each one returns whole tracks plus a prefix of the cut one. Six header errors (a cut header, a bad id, length 5, format 3, division 0, an SMPTE rate of -26) carry their offsets and have no restarts, so the function `use-partial-smf` returns `NIL`. Three corrupted bytes in track chunks are each reported at the right byte and track: an `F4` status byte, a status byte where a data byte belongs, and a data byte with no running status before it. The tempo change's type byte turned into a key signature gives a meta event of the wrong length. `skip-event` drops it and adds its delta to the next event, so the marker keeps its tick but the tempo map loses the change (the end moves to 48/5 s). `use-value` with a new tempo event restores an SMF `equalp` to the original. A last chunk without its end of track signals a `midi-format-warning` at the chunk's end, and writing the result appends the end of track again, giving back the original bytes.
6. **Bad values: `midi-encode-error`.** Construction already rejects an out-of-range key or delta with a `type-error` at SBCL's default safety. `write-smf` checks what the slot types let through, and reports the track and the offending element: a sysex data byte of 300, a lyric character above code 255, a 4/6 time signature, an end of track in the middle of a track, a (tick . event) pair left in a track, an unknown meta event using a known type byte, and format 0 with three tracks. A failed write to a pathname leaves no file behind.
7. **Files and streams.** `write-smf` to `twinkle.mid` and `read-smf` of the pathname. The file is checked to be byte-identical to the committed copy. Then the type-0 and type-1 versions are written one after the other to a single octet stream, and two `read-smf` calls read them back: each stops right after the last track chunk it needs (at positions 493 and 1020).
8. **Cross-read with mido.** `uv run --no-project --with mido==1.3.3 python -I -c ...` reads `twinkle.mid` with mido and prints what mido sees. mido agrees on the type, ticks per beat, track names, message count per track (8, 47, 37), note-on count, lyrics, and the length in seconds (10.8, against 54/5 from `ticks-to-seconds`).

None. The demo found no bug in midi-protocol 0.1.0.
