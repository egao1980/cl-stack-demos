# MIDI demo: Standard MIDI Files, and scores to and from them

`harness-demos-midi` is a tour of two libraries from GHCR, in two parts.

- **Part 1, midi-protocol 0.1.0** (sections 1-8). The library models MIDI 1.0 messages and reads and writes Standard MIDI Files (SMF) of type 0, 1 and 2. It works with files only: no real-time ports and no MIDI 2.0. Events are immutable structs, a track is a list of events, and an SMF is a header (format and division) plus a list of tracks. The part uses one short piece, "Twinkle, Twinkle, Little Star", whose tune and words are in the public domain. It builds the piece in code, writes it, reads it back, times it, breaks the bytes in several ways and repairs them, then lets mido read the result.
- **Part 2, score-backend-midi 0.1.0** (sections 9-13, slice SC4 of the score family). The library converts a [score-protocol](../score/) score to an SMF and back. Export writes a conductor track and one track and channel per voice. It plays repeats in score-protocol's `unfold` order, sounds a tie as one note, turns dynamics into velocities, writes lyrics as `FF 05` events and chord symbols as `chord:` text. Import quantises onsets to a grid chosen per beat through `sat-protocol:minimize`, spells pitches with music-theory, and gives every guess a confidence. The part builds a four-part OLD HUNDREDTH with two verses and exports it. It then makes a rehearsal set from it, reads it back, imports a humanised performance of a melody, and lets mido read the exported hymn.

Every result with a known answer is checked: 218 checks, 151 when uv is missing. The summary line reports the mismatches. The code is in [`src/demo.lisp`](src/demo.lisp) (part 1) and [`src/score.lisp`](src/score.lisp) (part 2). [`demo-output.txt`](demo-output.txt) is the output of the last run, on macOS arm64 with SBCL 2.6.9, with home and temp paths replaced by `~` and `<tmp>`. Two files that any MIDI player can play come from the run: [`twinkle.mid`](twinkle.mid) (527 bytes, part 1) and [`old-hundredth.mid`](old-hundredth.mid) (3880 bytes, part 2: the hymn with its repeat played out, a verse per pass).

The system pins score-backend-midi 0.1.0 and the versions it was built against: score-protocol 0.2.0, midi-protocol 0.1.0, music-theory 0.5.0, sat-protocol 0.2.0 and sat-backend-cdcl 0.1.0. These are lower bounds, and cl-repo resolved music-theory 0.5.1 for the committed run.

## Run

```bash
cd harness/midi
cl-repo run -- sbcl --non-interactive --no-userinit --eval '(require "asdf")' \
  --eval '(asdf:load-system "harness-demos-midi")' \
  --eval '(harness-demos-midi:run-demos)' > demo-output.txt 2>&1
```

It needs SBCL and `cl-repo`. Sections 8 and 13 also need [uv](https://docs.astral.sh/uv/) on `PATH`, and fetch mido 1.3.3 from PyPI on the first run. Without uv, both sections print a note and are skipped, as the two libraries' own tests skip their mido cross-reads. Apart from that one download there is no network step. A run takes about five seconds with `cl-repo run`, most of it start-up and the mido subprocesses. `run-demos` returns `NIL` when a check fails or a section stops on an error, and CI then exits 1.

## Part 1: what each section shows (midi-protocol 0.1.0)

1. **Build a type-1 SMF and write it.** The piece is in C major and 4/4, at 480 ticks per quarter note, and has two phrases of two bars. There are three tracks. The tempo track holds the title (`track-name-event`), time signature, key signature, tempo (100 bpm, then 80 bpm from bar 3) and two markers. The melody track is a flute on channel 0: track name, program change, volume and pan controllers, then for each note a `lyric-event` with the syllable, a `note-on-event` and a `note-off-event`. The bass track has root and fifth together on channel 1. Each track is built from (tick . event) pairs with `track-from-absolute`. `write-smf` with destination `NIL` returns 527 octets. The 14-byte header is dumped field by field. Each event of the tempo track is then shown with its file offset, delta and bytes, so you can see the delta time as a variable-length quantity (3840 is `9E 00`), the 24-bit tempo (`09 27 C0`), and the time signature's denominator stored as a power of two. The event bytes are checked against hand-written hex.
2. **Read it back.** `read-smf` returns an SMF that is `equalp` to the one written, and writing that again gives the same 527 bytes. Every event of the three tracks is listed with its delta, its absolute tick and a description. Events print readably as `#S(MIDI-PROTOCOL:NOTE-ON-EVENT ...)` and read back `equalp`. `copy-event` makes a changed copy (`:key`, `:channel`) and leaves the original as it was.
3. **Running status.** The file is written with and without `:running-status`: 527 against 545 bytes. A table gives the saving per track, which equals the number of channel events that repeat the status of the event before them. In the melody that is one byte, because every note-on follows a lyric (a meta event resets running status). In the bass it is 17 bytes, because the second note-on and the second note-off of each pair go without a status byte. The first bass events are shown encoded both ways (`00 2B 46` against `00 91 2B 46`). Both files read back to the same events, and the longer one written again with the default gives the shorter one byte for byte.
4. **Absolute time.** `track-to-absolute` and `track-from-absolute` round-trip the melody. Events at the same tick keep their input order, so pairs given in reverse put a note-on before the note-off of the same key at tick 480, which would cut the note short. `merge-tracks` makes the type-0 view: 90 events, 17 of them at tick 0 in track order, 493 bytes, every event at its original tick. `tempo-map` gives `((0 . 600000) (3840 . 750000))` for the piece and `((0 . 500000))` (`+default-tempo+`) for a track with no tempo event. `ticks-to-seconds` gives exact rationals: a table shows when each syllable is sung (`I` at 111/20 s, the end at 54/5 s), checked against a hand calculation, plus results with no tempo map and with SMPTE divisions (25 fps, and 29.97 drop frame). A type-2 SMF holds two independent patterns, the tune at 100 bpm and a copy a fourth up at 150 bpm. Each pattern gets its own tempo map, and the section shows what `tempo-map` returns for the whole type-2 SMF, where the tracks are merged.
5. **Bad bytes: `midi-parse-error` and its restarts.** A file cut 20 bytes short fails at offset 507 in track 2, with `skip-chunk` and `use-partial-smf` on offer. `use-partial-smf` keeps the two whole tracks and the start of the bass, and `skip-chunk` drops the bass. Every one of the 527 proper prefixes fails at its own length, and `use-partial-smf` on each one returns whole tracks plus a prefix of the cut one. Six header errors (a cut header, a bad id, length 5, format 3, division 0, an SMPTE rate of -26) carry their offsets and have no restarts, so the function `use-partial-smf` returns `NIL`. Three corrupted bytes in track chunks are each reported at the right byte and track: an `F4` status byte, a status byte where a data byte belongs, and a data byte with no running status before it. The tempo change's type byte turned into a key signature gives a meta event of the wrong length. `skip-event` drops it and adds its delta to the next event, so the marker keeps its tick but the tempo map loses the change (the end moves to 48/5 s). `use-value` with a new tempo event restores an SMF `equalp` to the original. A last chunk without its end of track signals a `midi-format-warning` at the chunk's end, and writing the result appends the end of track again, giving back the original bytes.
6. **Bad values: `midi-encode-error`.** Construction already rejects an out-of-range key or delta with a `type-error` at SBCL's default safety. `write-smf` checks what the slot types let through, and reports the track and the offending element: a sysex data byte of 300, a lyric character above code 255, a 4/6 time signature, an end of track in the middle of a track, a (tick . event) pair left in a track, an unknown meta event using a known type byte, and format 0 with three tracks. A failed write to a pathname leaves no file behind.
7. **Files and streams.** `write-smf` to `twinkle.mid` and `read-smf` of the pathname. The file is checked to be byte-identical to the committed copy. Then the type-0 and type-1 versions are written one after the other to a single octet stream, and two `read-smf` calls read them back: each stops right after the last track chunk it needs (at positions 493 and 1020).
8. **Cross-read with mido.** `uv run --no-project --with mido==1.3.3 python -I -c ...` reads `twinkle.mid` with mido and prints what mido sees. mido agrees on the type, ticks per beat, track names, message count per track (8, 47, 37), note-on count, lyrics, and the length in seconds (10.8, against 54/5 from `ticks-to-seconds`).


## Part 2: scores and MIDI files (score-backend-midi 0.1.0)

The score is OLD HUNDREDTH, the melody of Psalm 100 in the Genevan Psalter (Louis Bourgeois, 1551), in G major and the even rhythm of modern hymnals. The words are William Kethe's (1561), verses 1 and 2. The alto, tenor and bass are a plain chordal setting written for the demo. The score has one part, "Choir", with four voices on two staves: 4/4, quarter = 80, a half-note pickup and a half bar at the end. There are 32 chord symbols, among them G/B, D/F#, G/D and D7. Line 3 is marked p and line 4 f. The alto holds its D4 across the barline into bar 3 (a tie), and a repeat sign at the end plays the hymn twice. Both verses are on the soprano.

9. **Export.** The four voices are printed bar by bar, and `check-score` finds no issue. `(score-to-smf hymn :unfold nil)` plays every bar once, as written. It returns a format-1 SMF at 480 ticks per quarter note and warns `lossy-conversion` "ids". A table gives each track's name, instrument name, channel (0-3), program (52, Choir Aahs, the default), CC7 100, CC10 64, and its note and lyric counts. The conductor track is listed event by event, with each event's position (bar:offset):
   - the title and the copyright;
   - the time signatures 2/4 (the pickup), 4/4 and 2/4 (the last half bar), each from the bar's actual length;
   - the key signature (one sharp, major) and the tempo (750000 µs per quarter);
   - the first six of the 32 `chord:` text events.

   The first eight `lyric-event`s of the soprano are shown with their note-ons (`"peo-"` before `"ple"`). The velocities by line are 80 (mf, the default dynamic), 80, 49 (p) and 96 (f) in every voice. The tied alto D4s sound as one note, from tick 3840 to 5760, so the alto has 32 note events in the score and 31 notes in its track. `(score-to-smf hymn :verse :pass)` uses the default `:unfold t`. It plays the 22 bars of the `unfold` view, (0 . 1) to (10 . 1) and then (0 . 2) to (10 . 2): 38400 ticks, twice the notes and lyrics. No time-signature event is written at the turn, because bar 10 and the pickup are both 2/4. Bar 0's tempo mark is written again on pass 2. The soprano sings "and re- joice." and then "The Lord, ye know, is" from verse 2. This export is written to `old-hundredth.mid` and checked against the committed copy.
10. **Rehearsal set.** `rehearsal-mix` for the alto gives the `:mix` alist: velocity +20, CC7 127 and pan 64 for the alto, and +0, CC7 80 and pan 16 for the others. `(rehearsal-set hymn :verse :pass)` makes one SMF per voice. For each file, a table gives every voice track's note-on velocity on lines 1, 3 and 4, its CC7 and its CC10. The voice brought forward has 100/69/116 at 127 and 64, and the others 80/49/96 at 80 and 16. Each file is the size of the plain export. An unknown voice id signals `unknown-element`, and a `handler-bind` answers it through the `use-value` restart with the tenor's id.
11. **Round trip.** `import-midi` reads the as-written export (2076 bytes) back into a score. It gives no warnings and no `low-confidence-guess` signals. It restores the title and copyright, 11 bars from 0 to 10 with the pickup, 4/4, G major and quarter = 80. The four tracks share the instrument name "Choir", so they come back as one part with voices Soprano, Alto, Tenor and Bass. The sounding notes of each voice (onset, end and spelled pitch, with ties joined), the soprano's lyrics and the 32 chord symbols are compared with the original. **0 differences.** The imported alto cuts its long D4 at the barline into two tied pieces again. All 214 imported elements have provenance `:midi`, and `uncertain-elements` is empty. The section then lists what a MIDI file can't carry: ids, dynamics (only their velocities), the other metadata, stems, the two-staff layout and the repeat sign.
12. **Importing a performance.** The "Ode to Joy" melody (Beethoven, 1824; bars 1-4 and 9-12 of the theme, D major) is played at quarter = 100. Every onset is up to 20 ms early or late, each note is held for 90% of its value, and the velocities run from 70 to 90, all from a seeded generator. Bar 7 is varied with a triplet, F#4 G4 G#4 running up to A4. The file is format 0, 333 bytes, and has no time or key signature. The jitter of every note is listed. `quantize-onsets` chooses a grid for each beat, and the table shows each beat's onsets in ms, the chosen subdivision, the snapped positions and the confidences. The eighths of beats 4.2 and 6.2 choose 2, the triplet of beat 7.2 chooses 3, and every other beat stays on the quarter. Every onset snaps to its written position. With `sat-protocol:*sat-backend*` bound to `NIL`, each `minimize` call signals `sat-no-backend`. A handler gives it a CDCL backend through `use-backend` and counts the calls: 20 calls for the 25 beats with onsets, since beats with equal cost tables share one answer. With straight grids only, the triplet beat takes 16ths, with confidence 0.32. `import-midi` then builds the score, and a `handler-bind` logs its `low-confidence-guess` signals. The results:
    - The imported melody is printed with the triplet notes marked.
    - 4/4 was assumed (confidence 1/2). The key ranking from `detect-key` is D major 0.593, F# minor 0.546, E minor 0.507 and A major 0.493.
    - The spelling follows the key: 66 is F#4, and the chromatic 68 is G#4 (rule S4, rising to A4), with spelling confidence 14/45.
    - The uncertainty report has two elements, the first measure ("meter", 1/2) and the G#4 ("spelling", 0.311). These are exactly the logged ids, in document order.
    - No onset is in doubt: the least confidence from quantisation is 0.99. `check-score` finds no issue.
13. **Cross-read with mido.** `uv run --no-project --with mido==1.3.3 python -I -c ...` reads `old-hundredth.mid`. For each track it prints the name, channels, programs, note-on count, velocities, lyrics, first lyrics, text events, tempi, time signatures and key. Every value is checked against midi-protocol's own reading of the same SMF. mido's length, 60 s, matches `ticks-to-seconds`.

## Issues found

Part 1 found no bug in midi-protocol 0.1.0.

Part 2 found no bug in score-backend-midi 0.1.0: export, rehearsal sets, the round trip and the import all follow the file headers. One design follow-up was filed:

- [egao1980/score-backend-midi#4](https://github.com/egao1980/score-backend-midi/issues/4). A note outside the key gets the spelling confidence `1 - ambiguity`, and music-theory's ambiguity is the note's distance from the key centre, whichever rule decided the spelling. So nearly every chromatic note is flagged. In section 12 the G#4 that rule S4 spells correctly gets 14/45 and is one of the two entries in the uncertainty report.

The performance in section 12 ends well inside its last bar, so the late-last-note case of [#3](https://github.com/egao1980/score-backend-midi/issues/3) does not come up.
