# Harness demos

Runnable demos of the coding-agent harness work (plan: cl-workspace `docs/HARNESS-PLAN.md`), run against the **published GHCR packages** — evidence that each feature works, and a bug finder: anything a demo trips over is filed on the owning repo, not worked around.

Five cl-repo projects, one per area. Each `demo-output.txt` is the captured output of the last run (home and temp paths replaced with `~` / `<tmp>`).

## Run

From a project directory (dependencies come from GHCR through `cl-repo`; `--no-userinit` keeps a personal `~/.sbclrc` out of the image):

```bash
cd harness/data   # or fs, agent, code, image
cl-repo run -- sbcl --non-interactive --no-userinit --eval '(require "asdf")' \
  --eval '(asdf:load-system "harness-demos-data")' \
  --eval '(harness-demos-data:run-demos)' > demo-output.txt 2>&1
```

`HARNESS_DEMOS_MODEL=<exact LM Studio model id>` picks the model for every live step (`agent/` prompt cache, `code/`, `image/`) instead of each project's heuristic; it is used only when LM Studio answers, so CI still runs the mocks and skips. The output says which model ran and why (`from HARNESS_DEMOS_MODEL` or the heuristic). Unset, the heuristics are: `code/` a coder model, then one LM Studio marks `tool_use`; `image/` a coder model, then the first chat model; `agent/` a `2b`, then a `4b`, then any chat model. `HARNESS_DEMOS_BASE_URL` (default `http://127.0.0.1:1234/v1`) points the live steps at any OpenAI-compatible `/v1` server instead of LM Studio (for example an Unsloth or llama.cpp server on another host). `HARNESS_DEMOS_API_KEY` is the bearer key for it; unset, the key is `LM_API_TOKEN` from the environment or the workspace `.env`, and an empty or absent key sends no `Authorization` header. The LM Studio-only `/api/v0/models` capability probe (`code/`) is optional: when it is missing or fails, the plain `/v1/models` id list is used and tool use counts as unknown (`HARNESS_DEMOS_MODEL` wins anyway). `MODEL THAT RAN` names the server's host; the key is never printed. The committed outputs ran with `HARNESS_DEMOS_MODEL=qwen/qwen3.8-27b` on the default endpoint, just before the endpoint variables were added, so their `Model` header still reads `LM_API_TOKEN found` and `MODEL THAT RAN: LM Studio <id>` without the host (a rerun after the change could not run: the LM Link host went offline and then failed to load the model):

```bash
HARNESS_DEMOS_MODEL=qwen/qwen3.8-27b PATH=/opt/homebrew/bin:$PATH cl-repo run -- sbcl … > demo-output.txt 2>&1
```

Needs: SBCL via Roswell, `cl-repo`, `git` (≥ 2.43 for `fs/`; ≥ 2.56 for `code/`, whose plan areas are git worktrees through revision-backend-git 0.4.0) and `jj` 0.47.1 for `fs/` and for `code/` Demo j (jj); without jj that step is skipped with a printed reason. The prompt-cache step in `agent/` talks to a local LM Studio (`http://127.0.0.1:1234/v1`, token from `LM_API_TOKEN` in the workspace `.env`; it is never printed) and reports that it was skipped when no server is reachable. `code/` uses the same server and token when a model is loaded, and a scripted mock provider otherwise (its interactive Demo f always runs on a scripted streaming mock, plus one LM Studio turn when a model is there; the plan-mode Demos g and h always run on the scripted mocks, and Demo i is a real-model plan run that is skipped without a model). `image/` spawns Swank images with `ros +Q run` (lisp-mcp's default `repl-spawn` command; swank and slynk come from cl-repo as `:ci :with` install roots) and runs its real-model step only when LM Studio answers.

## What each set shows

- **data** — unified diffs, three-way merge with conflict markers (default and `:diff3`), tree diffs with rename and mode changes, parsing real `git diff` output and applying / inverting it; a revision DAG with tags and as-of, a ref conflict resolved through the `retry` restart, plans and drift on a target, merge projections resolved with `take-ours`, composite restore (now with a caller `:id`); complete schema diffs and a SQLite table rebuild that keeps rows; migrations with offline SQL and a failing step that is both `step-failed` and `sqlite:sqlite-error`, resumed with `retry-step`.
  - **Demo 5, diff-backend-lisp-source** — a real file, process-protocol's `src/protocol.lisp` at 0.3.0 and 0.4.0 (committed under [`data/fixtures/`](data/fixtures/)): its top-level forms as units (header comments travel with their form), the 0.3.0 → 0.4.0 diff at `:summary` / `:changes` / `:content` (form adds, nested leaf edits such as `defun kill/2`), `unified-patch` with a path, byte-for-byte apply / invert / `:sexp` round trip; a comment edit, a rename (`alive-p` → `live-p`) and a move; a three-way merge of the real 0.4.0 change with edits to other forms (clean, symmetric) and against an edit of the same `defun kill` (one conflict, the two sides rendered with the `:text` engine); `lisp-source-unreadable` falling back through `use-text-diff`.
  - **Demo 6, diff-protocol 0.3.0 engine API** — an `:env` engine written in the demo (states are alists of strings, not text) registered with `register-diff-engine`, with `apply-change` and `render-unified-content` only: `:unified` of its own diffs, `parse-diff :sexp` finding it by name, diff-protocol's `skip-change` restart on a stale state, the default `merge-states` (one clean key, one conflict), and `.env` files in a tree diff rendered as hunks instead of `Binary files … differ`.
- **fs** — ranged reads, compare-and-swap writes with restarts, `.gitignore` walk / grep, content-addressed snapshots and restore, a sandboxed area seeing an external shell edit and committing past a conflict; binary process output, env merge vs replace, octet streams, timeouts; the git backend (commits, refs, diffs, a working copy whose drift is captured without touching the worktree or index, a read-only revision filesystem) and the jj backend (change ids across rewrites, as-of via the operation log, conflicted revisions).
  - **Demo 5, cl-stack-pathlib 0.6.1** — fnmatch globs (`?`, `[0-9]`, `[!0-9]`, escaped `\[x\]`, `**`, `rglob`) giving the same results on the local and the memory filesystem, `match-p`; probes on a file, a directory, links to each, a dangling link and a link cycle (`stat(2)` vs `lstat(2)` views, `symlink-loop` as a `path-error`). The `rglob` checks in Demo 1 now pass (cl-stack-pathlib#28 fixed in 0.6.0).
  - **Demo 6, process-protocol 0.4.0** — `supports-p`, `process-pid`; a shell whose background child (the grandchild) survives a plain `kill` but is stopped by `:process-group t` + `kill :tree t` (both in the shell's process group, checked with `ps -o pgid=`); `run :process-group t :timeout 1` whose grandchild never writes its marker; `kill :tree t` on a handle without a group signalling `process-group-error` with a `continue` restart.
  - **Demo 7, cl-stack-pathlib 0.9.0 change journals (R4b)** ([`src/journal-demo.lisp`](fs/src/journal-demo.lisp)) — fs-backend-darwin 0.1.0 and fs-backend-linux 0.1.0 load and register on every OS, so `watch-mechanisms` lists `:fsevents :inotify :poll` everywhere and `:auto` picks `:fsevents` on macOS, `:inotify` on Linux and `:poll` on Windows (the other mechanism signals `unsupported-operation`); close is idempotent and a drain after close signals `journal-error`. A watched tree edited by pathlib, `rename-file` across directories, a delete, a new nested directory and a child `sh` (process-protocol) gives one drain with exactly the touched relative paths and `complete-p` T (an untouched sibling stays out; the next drain is `(nil t)`). An area with `:journal :auto` over 2000 files, three rounds of five edits: `fs-area-changes` is EQUAL to `:rescan t` after every call (the law), with both timings printed next to the mechanism's idle drain floor (FSEvents 0.1.0 waits ≈ 50 ms per drain, so on macOS the journal call is ≈ 50 ms + a few ms of narrowed re-examination against ≈ 70 ms of full rescan). Incomplete drains: `:poll` answers `(nil nil)` and its area falls back to the full rescan; an overflow injected through the backend's test hook (FSEvents MustScanSubDirs, inotify `IN_Q_OVERFLOW`) gives one `(nil nil)` drain, the same answer, then complete drains again. Last, `run-journal-suite` for the active mechanism (19 steps on macOS and Linux, including the 2000-file burst and the child-process step). Any law break fails the demo. The end of `fs/demo-output.txt` has a Linux run of this demo (ci-base container, `:inotify`: no drain floor, so the journal call is ≈ 4 ms against ≈ 57 ms of full rescan).

## Windows

All five projects run on windows-latest in CI. The POSIX tools come from Git for Windows on PATH (`sh`, `env`, `printf`, `cat`, `sleep`); temp directories are cleared of read-only attributes (git objects) before deletion, including the code project's scratch directory, which holds the real git repositories of the plan demos. Skipped there, each with a printed reason: fs Demo 5 symlink probes (no `fs-create-symlink` on Windows), fs Demo 6 process-group / tree-kill steps (POSIX groups and signals), agent Demo 4b (the pty child; Unix-only by design). Agent Demo 7 runs the shell tools with Git for Windows' `sh` instead of `cmd.exe` (executor `:process`). The image project loads its demo system through `uiop:parse-native-namestring` (a native Windows path is not a Lisp namestring) and retries deleting its scratch directory (lisp-mcp#18). So does the code project. The real cause was egao1980/repl-protocol#11: on Windows `ros.exe` runs SBCL as its child, so a kill reached only `ros.exe` and the image kept its working directory in use. repl-protocol 0.2.8 kills the whole tree, and both projects pin it.
