# Harness demos

Runnable demos of the coding-agent harness work (plan: cl-workspace `docs/HARNESS-PLAN.md`), run against the **published GHCR packages** — evidence that each feature works, and a bug finder: anything a demo trips over is filed on the owning repo, not worked around.

Forty-one cl-repo projects, one per area, and two screen recordings. Each `demo-output.txt` is the captured output of the last run (home and temp paths replaced with `~` / `<tmp>`).

## Run

From a project directory (dependencies come from GHCR through `cl-repo`; `--no-userinit` keeps a personal `~/.sbclrc` out of the image):

```bash
cd harness/data   # or fs, agent, code, image, supervisor, isolation, css, acp, policy, unkernel, eval, canvas, sample, music-theory, sat, logic, pdf-render, midi, cl-repo (after its scripts/setup.sh), score, musicxml, score-parity, engrave, documents, cache-ttl, mime-multipart, http-facade, dexador-http, browser, llama-grammar, imports, image-ops, s3-minio (through its scripts/run.sh, which starts MinIO), mcp-host, audio, sat-sessions (zed-sample: ./rehearse.sh)
cl-repo run -- sbcl --non-interactive --no-userinit --eval '(require "asdf")' \
  --eval '(asdf:load-system "harness-demos-data")' \
  --eval '(harness-demos-data:run-demos)' > demo-output.txt 2>&1
```

`HARNESS_DEMOS_MODEL=<exact LM Studio model id>` picks the model for every live step (`agent/` prompt cache, `code/`, `image/`) instead of each project's heuristic; it is used only when LM Studio answers, so CI still runs the mocks and skips. The output says which model ran and why (`from HARNESS_DEMOS_MODEL` or the heuristic). Unset, the heuristics are: `code/` a coder model, then one LM Studio marks `tool_use`; `image/` a coder model, then the first chat model; `agent/` a `2b`, then a `4b`, then any chat model. `HARNESS_DEMOS_BASE_URL` (default `http://127.0.0.1:1234/v1`) points the live steps at any OpenAI-compatible `/v1` server instead of LM Studio (for example an Unsloth or llama.cpp server on another host). `HARNESS_DEMOS_API_KEY` is the bearer key for it; unset, the key is `LM_API_TOKEN` from the environment or the workspace `.env`, and an empty or absent key sends no `Authorization` header. The LM Studio-only `/api/v0/models` capability probe (`code/`) is optional: when it is missing or fails, the plain `/v1/models` id list is used and tool use counts as unknown (`HARNESS_DEMOS_MODEL` wins anyway). `MODEL THAT RAN` names the server's host; the key is never printed. The committed `code/` output is the 0.8.0 rerun on local LM Studio `qwen3.5-2b` (see code below). The committed `agent/` and `image/` outputs (and the code output before it, in git history) ran against an Unsloth Studio server on another host on the LAN (OpenAI-compatible, llama.cpp underneath, no `/api/v0`), model `unsloth/Qwen3.8-Flash-Next-GGUF` (UD-IQ4_XS, a 125B mixture of experts with about 6B active, a reasoning model), loaded with `n_ctx` 65536 in one slot, so requests queue one at a time. It reads prompts at about 73 tokens/s and generates about 12 tokens/s:

```bash
HARNESS_DEMOS_BASE_URL=http://<host>:8888/v1 HARNESS_DEMOS_API_KEY=… \
```
