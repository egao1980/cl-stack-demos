== 1. Chrome's JSON and base64 go through the stack (#1)
========================================================================
0.1.0 parsed CDP JSON with a private parser whenever no json-protocol backend
was bound, and that parser could not read `false`: Chrome's Page.navigate reply
("isDownload":false) failed with "bad JSON false". 0.2.0 depends on
json-protocol + json-backend-jzon and encoding-protocol; the private parser and
base64 are gone.

== 3. Replies are matched by id while events arrive (#2)
========================================================================
CONNECT-BROWSER sent Target.setDiscoverTargets; Chrome answers with a
Target.targetCreated event per target before the reply. 0.1.0 took the first event
as the reply and every later EVAL-JS read the next event (NIL, NIL, NIL). 0.2.0
reads until the reply with its id and keeps the events in a bounded buffer.

  Target.targetCreated events buffered   3: page, browser_ui, service_worker

  ok       eval-js 1+1, 2+2, 3+3: (2 4 6)

== 5. Events: ON-CDP-EVENT and WAIT-FOR-CDP-EVENT
========================================================================
Handlers run on the reading thread for every event read while a command or a
wait reads. Events are also kept in a bounded buffer, and WAIT-FOR-CDP-EVENT
takes the oldest matching one from it first, so an event that came in during the
previous command is not missed. :test narrows the wait.

  ok       eval-js "console.log('hello from the page'), 42": 42
  ok       the handler saw the console event: ("hello from the page")
  ok       wait-for-cdp-event: the buffered one first: "hello from the page"
  the :test wait returned after          0.3s
  ok       its message: "later"
  ok       the handler saw both: ("hello from the page" "later")
