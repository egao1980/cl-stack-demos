== 1. The mail layout, printed
==============================================================================
  The layout every mail client sends: a text body with an HTML alternative, and
  an attachment. Built with make-multipart-entity / make-text-entity /
  make-binary-entity and SET-HEADER (names stored lowercase), then PRINT-MIME:

    | From: ann@example.com
    | To: bob@example.com
    | Subject: Weekly report
    | Message-ID: <weekly-1@example.com>
    | MIME-Version: 1.0
    | Content-Type: multipart/mixed; boundary=mixed-91c2
    | 
    | --mixed-91c2
    | Content-Type: multipart/alternative; boundary=alt-7f3a
    | 
    | --alt-7f3a
    | Content-Type: text/plain; charset=utf-8
    | Content-Transfer-Encoding: 8bit
    | 
    | Hello Bob,
    | the weekly report is attached.
    | 
    | --alt-7f3a
    | Content-Type: text/html; charset=utf-8
    | Content-Transfer-Encoding: 8bit
    | 
    | <p>Hello Bob,<br>the weekly <b>report</b> is attached.</p>
    | 
    | --alt-7f3a--
    | 
    | --mixed-91c2
    | Content-Type: application/pdf
    | Content-Disposition: attachment; filename=report.pdf
    | Content-Transfer-Encoding: base64
    | 
    | JVBERi0xLjcKJeLjz9MKAQID/w==
    | --mixed-91c2--
    | 

  730 octets, 33 lines, every one ending in CRLF (0 bare LF).

== 3. Edge cases: prefix boundaries, line breaks, LF-only, preamble
==============================================================================
  an inner boundary "b2" that has the outer "b" as a prefix ("--b" inside
  "--b2" does not end the outer part):
    multipart/mixed
      multipart/mixed
        text/plain  "in"
      text/plain  "out"

  part contents that end, or are made of, line breaks, each round-tripped alone:
    ""                         -> ""
    "x"                        -> "x"
    "\r\n"                     -> "\r\n"
    "a\r\n\r\nb\r\n"           -> "a\r\n\r\nb\r\n"
    "--not-the-boundary\r\n"   -> "--not-the-boundary\r\n"

  an LF-only message (no CR at all):
      text/plain  "one"
      text/html  "<p>two</p>"

  a preamble, a part with no headers (it starts with the blank line) and an epilogue:
    preamble "This is the preamble.", part "no headers in this part", epilogue "the epilogue"
    the headerless part's type: (no Content-Type) (RFC 2045 says text/plain; filed as
    egao1980/mime-protocol#13)

== 4. Canonical header names on print, case-insensitive lookups
==============================================================================
  The model keeps names lowercase; PRINT-MIME writes them with CANONICAL-HEADER-NAME:
    from                         -> From
    subject                      -> Subject
    mime-version                 -> MIME-Version
    message-id                   -> Message-ID
    content-transfer-encoding    -> Content-Transfer-Encoding
    content-md5                  -> Content-MD5
    dkim-signature               -> DKIM-Signature
    x-mailer                     -> X-Mailer
  lookups stay case-insensitive: header-value MIME-Version / mime-version / MIME-VERSION -> ("1.0" "1.0" "1.0")

== 6. A browser's form-data part headers: UTF-8 names, a literal backslash (#14)
==============================================================================
  A form posted by Chrome or Firefox: a text input named имя, file inputs holding
  Prélude.svg, a\b.svg and say "hi".svg, and a FormData field named "a\nb". The
  body exactly as sent, octets above 7F written as \xHH:

    | --b
    | Content-Disposition: form-data; name="\xD0\xB8\xD0\xBC\xD1\x8F"
    | 
    | Pr\xC3\xA9lude
    | --b
    | Content-Disposition: form-data; name="u"; filename="Pr\xC3\xA9lude.svg"
    | Content-Type: image/svg+xml
    | 
    | <svg/>
    | --b
    | Content-Disposition: form-data; name="w"; filename="a\b.svg"
    | Content-Type: image/svg+xml
    | 
    | <svg/>
    | --b
    | Content-Disposition: form-data; name="q"; filename="say %22hi%22.svg"
    | Content-Type: image/svg+xml
    | 
    | <svg/>
    | --b
    | Content-Disposition: form-data; name="a%0D%0Ab"
    | 
    | x
    | --b--

  PARSE-MIME, then disposition-name / disposition-filename of each part:

    "имя"
    "u" / "Prélude.svg"
    "w" / "a\b.svg"
    "q" / "say "hi".svg"
    "a\r\nb"

  0.3.0 read the header octets as ISO-8859-1 and a backslash as an RFC 822
  quoted-pair. Both readings, as they still apply elsewhere:
    the UTF-8 octets of Prélude.svg read as ISO-8859-1  -> "PrÃ©lude.svg"
    attachment; filename="a\b.svg" (quoted-pairs stay) -> "ab.svg"

  a field whose octets are not UTF-8 stays ISO-8859-1: filename="caf\xE9.txt" -> "café.txt"

  Our own encoders. http-protocol's multipart writes FORMAT-FORM-DATA-DISPOSITION
  as UTF-8; it adds filename*, which still wins:
    form-data; name="file"; filename="Prélude.svg"; filename*=UTF-8''Pr%C3%A9lude.svg
    -> filename "Prélude.svg", filename* "UTF-8''Pr%C3%A9lude.svg", disposition-filename "Prélude.svg"

  make-form-data + print-mime quotes them the browser way too:
    | Content-Disposition: form-data; name=w; filename="a\b.svg"
    | Content-Disposition: form-data; name=q; filename="say %22hi%22.svg"
    "w" / "a\b.svg"
    "q" / "say "hi".svg"

== 7. The same form read by python-multipart and werkzeug
==============================================================================
  The section 6 body, read by python-multipart 0.0.34 and werkzeug 3.1.9 (Python 3.13.18).
  "same" means the same (name filename) as mime-protocol:

    mime-protocol 0.3.1              python-multipart             werkzeug
    "имя"                            same                         same
    "u" / "Prélude.svg"              same                         same
    "w" / "a\b.svg"                  same                         "w" / "ab.svg"
    "q" / "say "hi".svg"             "q" / "say %22hi%22.svg"     same
    "a\r\nb"                         "a%0D%0Ab"                   "a%0D%0Ab"

  All three read the UTF-8 octets as UTF-8. python-multipart also keeps the
  backslash, and leaves %22 %0D %0A to the application. werkzeug decodes %22,
  keeps %0D %0A, and drops the backslash: it unescapes quoted-pairs, which is
  what mime-protocol 0.3.0 did.
